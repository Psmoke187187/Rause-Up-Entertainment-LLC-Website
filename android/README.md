# Raise Up Entertainment native Android candidate

This Java Android project preserves `com.raiseupentertainment.app`, Raise Up Entertainment LLC's name, website domain and dark/gold branding. It is a local candidate, not an uploaded or published Play release. The owner has a draft Play listing and merchant profile, but payout setup, Google Play products, server deployment and device/payment testing still need completion.

The app has native Beats, Sound packs, My licenses and Help screens; search; public protected preview playback with a 45-second cap; native license/privacy text; and support-email composition. There is no WebView, digital purchase link to the website, Stripe SDK or general website navigation. The domain appears as branding. Support opens the user's email composer and does not send automatically. Private masters/licenses and credentials are not bundled.

## Build

Declared toolchain: Android Gradle Plugin 8.13.2, Gradle 8.13, JDK 17, compile/target SDK 36, minimum SDK 23 and Google Play Billing 9.1.0. Gradle dependencies come from Google Maven and Maven Central. The Kotlin 1.8.22 BOM aligns the transitive standard-library modules to prevent duplicate legacy JDK7/JDK8 classes. Install tools inside the task workspace or use an existing authorized Android Studio setup; no global installation is necessary. Gradle wrapper files can be generated using the verified Gradle 8.13 distribution; no unverified wrapper binary is included in this source.

Run `node tools/sync-catalog.mjs` after the website has exported `data/android-catalog.json`; this copies only native metadata and policies into the bundled read-only snapshot and forces `billingEnabled=false`. It strips any unrelated web checkout fields. The live catalog comes from `https://raiseupentertainmentllc.com/data/android-catalog.json`; an offline/bundled catalog never enables purchases.

On Windows, use `./build.ps1 -JavaHome ACTUAL_JDK17_DIRECTORY -GradleHome ACTUAL_GRADLE8_13_DIRECTORY -SdkRoot ACTUAL_ANDROID_SDK_DIRECTORY`. This runs meaningful policy unit tests, Android lint, a debug APK build and an unsigned release App Bundle build. Signing/uploading a release requires the owner's proper Play signing configuration and a confirmed version code; no production signing key is created here.

The Windows Gradle build is blocked by Java `Path.toRealPath` returning AccessDenied for the installed SDK's `core-for-system-modules.jar`, despite ordinary file reads and granted parent access. The isolated Linux build below successfully compiled the candidate, ran its tests and lint, and produced a debug APK and unsigned release bundle.

## Payment behavior

Prices come only from Google Play `ProductDetails`, using an eligible matching buy purchase option. Rent/preorder offers are rejected. Missing/unfetched products remain unavailable. Immediately before purchase, the app refreshes the specific offer, displays its Google Play price and the native license for explicit acceptance, then asks the server to record a verified account-bound checkout intent and product readiness before opening Play's confirmation. Obfuscated account IDs use a SHA-256 hash of the verified server account ID, not the user's plaintext email.

Purchases require all of: `BILLING_RELEASE_ENABLED=true`, `SERVER_VERIFICATION_READY=true`, a configured delivery origin, fresh online catalog `billingEnabled=true`, matching server health/package, an eligible Play offer, the exact agreement version, a verified delivery account, and a ready server checkout intent. The candidate ships both BuildConfig release gates false and its delivery origin empty. The local Cloudflare backend now implements the Android routes in `../raise-up-website/backend/cloudflare/src/android.mjs` and Google verification in `play-api.mjs`; no route has been deployed or tested against an actual Play purchase. Its separate launch flags also remain false.

The client handles pending, cancellation, unavailable offers and service errors. It restores active non-consumed purchases on reconnect/resume and on the user's request. Pending receipts are submitted for durable server reconciliation, but never issue files. A `PURCHASED` callback is sent for server verification; it alone never establishes entitlement. The client never acknowledges or consumes purchases. The implemented server verifies using the Play Developer API, durably records the matching order and agreement, then acknowledges within Google's deadline. It retries failed acknowledgement and delivery, deduplicates globally by purchase token, and revokes download access for refunds/voided purchases. The app reports email delivery as complete only when the server returns `verified=true` and `deliveryStatus='sent'` for the exact product.

Products use non-consumable one-time buy options. This supports restoring one owned license per product/account. Selling additional one-song licenses to the same account requires a separately designed server-backed consumption/product workflow; this candidate does not silently consume ownership or manufacture new restore history. Exclusive ownership purchases remain unavailable.

## Server contract required before enabling purchases

These paths have a local, tested backend implementation but are not currently deployed endpoints. All use the compiled HTTPS delivery origin, reject redirects, and return bounded JSON. No arbitrary catalog-supplied endpoint is accepted.

| Route | Required behavior |
| --- | --- |
| `GET /android/health` | Return `googlePlayBillingReady:true` and the exact `packageName` only after Play credentials, catalog/release mapping, verification, acknowledgement and private delivery tests are ready. |
| `POST /android/accounts/email/start` | Receive email/legal name, validate/rate-limit them and send a short-lived code to that address; return an opaque challenge ID. Do not treat the unverified address as an account. |
| `POST /android/accounts/email/verify` | Verify the challenge/code and return `verified:true`, `accountId`, verified `email`, expiring `accessToken`, and `expiresAt` in Unix seconds. Native tokens are encrypted with the device's Android Keystore and excluded from backups/logs. |
| `POST /android/checkouts` | Authenticate the account, receive `productId`, `agreementVersion`, `termsAccepted:true`, validate the exact available master/archive and license, and durably record acceptance. Return `status:'ready'`, exact product/agreement IDs, `checkoutIntentId`, `obfuscatedAccountId=SHA256('raiseup-play-account-v1:'+accountId)` and `obfuscatedProfileId=SHA256('raiseup-play-intent-v1:'+checkoutIntentId)`, both lowercase 64-character hex. The phone validates these and passes both to Billing. No paid-ready response before the product is deliverable. |
| `POST /android/purchases/verify` | Authenticate the verified account; independently verify `packageName`, product, purchase token, account/profile binding, quantity, payment state and prior durable checkout agreement against Play. A nullable `checkoutIntentId` allows restore only when Google's profile hash identifies this buyer's original valid acceptance/order; never invent terms acceptance from a restore callback. Deduplicate tokens across users. PENDING returns `verified:false,status:'pending'` after storing only an encrypted reconciliation record. Return exact `productId` and `agreementVersion`, `verified:true`, opaque `orderId` (8–200 ASCII letters/digits/underscores/hyphens), and actual `deliveryStatus` only after fulfillment has been durably recorded. Only `deliveryStatus:'sent'` may confirm completed email delivery. |
| `GET /android/library` | Return only this authenticated account's verified, unrevoked licenses/orders as `orders`, with product title, agreement version and actual delivery status. Future download/resend actions must authenticate and bind each order rather than accept arbitrary URLs. |
| `POST /android/accounts/delete` | Authenticate the account and require `deleteAccount:true`; remove the delivery profile and all sessions, revoke private library/download access, and return `deleted:true`. Necessary transaction/license records remain separate for accounting, rights and disputes under a reviewed retention policy. The native Help screen asks for explicit confirmation first. |

Account credentials, Play service-account access and private storage credentials belong only on the server. The server collects a verified delivery address; Google Play purchase callbacks do not supply the buyer's email. Six-digit email challenges last ten minutes, permit five attempts and can be used once; opaque server sessions expire after thirty days and the phone encrypts them with its Android Keystore. The backend separately accepts authenticated Google Pub/Sub pushes at `/android/notifications/play`; this is not a phone endpoint. Configure one-time events, exact audience/subscription/service identity and verify the real setup before `PLAY_RTDN_CONFIGURATION_VERIFIED=true`. Durably queued notifications and PENDING tokens let one-minute Cron complete payment/delivery while the app stays closed. Every result still requires an independent Google purchase check and the original profile-bound acceptance. Purchase tokens are globally deduplicated and encrypted on the server for acknowledgement retries and refund checks. See the Cloudflare backend README for setup and owner attention for refund-review notices.

The backend rechecks Google at email/download/library access and polls the official voided-purchases feed. License pricing refers to the Google Play receipt; ProductsV2 does not return a paid amount, so the backend does not manufacture USD pricing for a regional Play payment. Production account-deletion/retention policy, public deletion access/support, accurate Play Data safety declarations and actual Google/Gmail/Cloudflare tests remain required before enabling purchases. The native privacy text describes this gated candidate and is not a substitute for a complete public privacy policy.

## Validation and remaining work

Unit tests cover stable distinct product IDs matching the exported catalog, malformed per-product metadata, rejection of payment/master/off-domain preview URLs, every purchase gate, account expiry/header-safe session tokens, pending/invalid receipt states, exact server product/license/order matching, and email-delivery status. Build/lint/device outcomes must be recorded separately after tools are available. Real Play testing must use an uploaded closed/internal-test bundle, licensed testers, configured products and server verification. Test successful, pending, canceled, restored, duplicate-token, refunded and failed-email cases; verify per-product file/license correspondence. Inspect narrow screens, screen readers, rotation, background/resume and playback errors. A local APK build does not prove Play policy approval or payment delivery.
